# Hospital Analytics — Chart-by-Chart Audit

## Purpose & methodology

This document is a complete, panel-by-panel audit of every visualization currently rendered on the **hospital (Type A) analytics** side of SugboDoc. It exists to be the factual foundation for the planned redesign (shared synthetic dataset, dashboard hierarchy reorganization, consistent drill-down, sorting controls, and genuinely multi-dimensional charts). Nothing here is a proposal to rebuild the site — the explicit rule applied throughout is *do not replace a chart simply because another chart type exists; preserve charts that already communicate their intended information effectively.*

**Scope.** Hospital analytics routes only. LGU / City-Health routes (`src/routes/lgu.analytics.*`) are deliberately excluded from this pass, as are the 8 LGU-side charts (13–20) inside `Top20NewCharts.tsx`.

**Method.** Every row below was written after reading the following files in full, not from memory or inference:

- `schema.md` (repo root) — the verified data-schema reference; every **Data Source** cell cites a table/field documented there.
- `src/routes/analytics.executive.tsx`
- `src/routes/analytics.clinical.tsx`
- `src/routes/analytics.revenue.tsx`
- `src/routes/analytics.claims.tsx`
- `src/routes/analytics.quality.tsx`
- `src/routes/analytics.laboratory.tsx`
- `src/routes/analytics.cohorts.tsx` (+ `src/components/analytics/cohort-builder.tsx`)
- `src/routes/analytics.patterns.tsx` (+ `src/components/analytics/temporal-heatmap.tsx` usage)
- `src/routes/analytics.alerts.tsx` (+ `src/components/analytics/alert-center.tsx`)
- `src/routes/analytics.new-charts.tsx` → `src/components/analytics/Top20NewCharts.tsx` (hospital charts 1–12 only)
- `src/components/analytics/interactive.tsx` — to establish exactly what `InteractiveChartCard`, `ChartDrillDrawer`, `GlobalFilterBar`, `ZoomControls` and `CompareToggle` actually do.

**Interaction claims are code-verified.** "Has drill-down" means an `onClick`/`onCellClick` handler that opens a `DrillDrawer` / `ChartDrillDrawer` / inline `DetailPanel` was found in the source. "Has sorting" means a user-facing sort control exists — note that `InteractiveChartCard`'s sorting only applies inside its *"View as table"* mode, never to the chart itself; that distinction is preserved in every Sorting cell.

**Column key.** *Multi-dimensional?* follows the supervisor's definition: a chart is multi-dimensional only when it presents **multiple meaningful analytical variables in one view** (e.g. category × time × magnitude), not when it merely uses colour or size decoratively. *D3 Opportunity* is assessed on general D3.js capability (there is no `d3.md` in this repo — confirmed absent); the default answer is "None" unless there is a real capability gap Recharts and the existing hand-rolled SVG components cannot close.

**A note on drill-drawer charts.** Where a drawer opens a genuinely different analytical view (e.g. ALOS broken down three ways), it gets its own row. Purely decorative in-card sparklines and gauges are noted inline on their parent row.

### Cross-cutting findings

**1. Sorting is almost entirely absent — 0 of 87 charts have a user-facing sort control on the chart itself.** Four panels (all on the Executive dashboard) offer column sorting, but only inside `InteractiveChartCard`'s "View as table" mode, never on the chart. Five more (Revenue by Department, Case Rate Coverage, Abnormal Result Rate, LOINC Unmapped, and several Top20 previews) are sorted correctly but the ordering is **hard-coded in the mock file or the render function**, so the user cannot re-rank by a different measure. The Cohort Builder is the starkest case: its results table uses `ReportTable`, which fully supports sorting, and the route explicitly disables it with `sort={null}` and `onSortChange={() => undefined}`. At least 30 of the 87 panels have a naturally rankable primary dimension and no way to rank it.

**2. Drill-down exists on 43 of 87 panels (49%), and uses three incompatible patterns.** A further 5 panels are themselves the terminal contents of a drawer, and 6 are genuinely flat data with nothing further to reveal; the remaining 33 have a meaningful drill path available in the schema and simply do not implement it. Of the 43 that do drill, the Executive and Patterns pages use `ChartDrillDrawer` (with CSV/PDF export and a "View Full Report" link); Clinical, Revenue, Claims, Quality and Laboratory use the plainer `DrillDrawer` (no export, no report link); the 12 new-charts previews use an inline `DetailPanel` that is not a drawer at all. Beyond the inconsistency, most drill paths are one level deep and terminal — of the 43, only the Clinical heatmap, the Claims pipeline and the Revenue funnel reach true encounter/claim-level rows. Several drills are also degraded or broken: the Executive denial-reason table drills to a generic "Denied" bucket without passing the reason code; the Quality HAC control chart's dot handler passes a permanently empty `period` string so point clicks find no data; every Laboratory KPI drawer renders the same "connect the module" placeholder.

**3. The global filter bar exists on exactly one page and changes almost nothing.** `GlobalFilterBar` appears only in `analytics.executive.tsx`, offering department and physician. Its output filters just two things — the admissions row list and a recomputed top-diagnoses count. Volume, revenue, payer mix, claims status and lab compliance are all rendered from unfiltered data on the same screen, so a department filter produces a screen that is internally inconsistent. The date-range picker is wired to state and used by nothing at all. The other nine hospital routes have no global filter whatsoever; their only filtering is per-panel and local (Quality's HAC category tabs, Clinical's ICD code picker, Revenue's collection-view tabs, Patterns' OPD/Emergency toggle, Alerts' severity tabs, and the Cohort Builder's criteria panel).

**4. Physician-level and doctor-level comparison is the weakest analytical axis on the site.** Only three panels compare doctors at all — Clinical's Surgeon Performance table, Claims' Physician Claims Performance table, and Quality's SSI funnel plot — and two of the three are unsorted HTML tables rather than charts. Meanwhile `AdmissionRow.physician`, `HeatmapDrillCase.physician`, `ReadmissionCase.physician`, `PhysicianClaimRow`, `SsiSurgeon`, `SurgeonRow`, `FormularyRow.physician`, `DenialRow.physician` and `PhysicianActivityRow` all carry the dimension. The Top20 preview's Physician Productivity Quadrant (chart 3) is the only proper multi-dimensional doctor comparison in the entire module, and it lives on an unlinked preview page. Volume adjustment is also inconsistent: the SSI funnel plot correctly adjusts for case volume, while the surgeon and physician tables rank raw rates with no denominator guard.

**5. There is substantial cross-page redundancy, and it is type-level, not just visual.** Payer mix is rendered twice (Executive "Revenue Breakdown" and Revenue "Payer Mix"), payer trend twice, and the two pairs are backed by *independently declared* `PayerSlice` and `PayerTrendPoint` interfaces in `executive.mock.ts` and `revenue.mock.ts` with identical shapes (documented in `schema.md` Known Cross-File Inconsistencies #3). Denial reasons appear on both Executive and Claims via two different types (`DenialReason` vs the richer `DenialReasonRow`). Alerts appear on both Executive (`ActionAlert`) and the Alert Center (`AlertItem`). Claims pipeline state appears as `ClaimStatusSlice` (Executive), `PipelineStage` (Claims) and `FunnelStage` (Revenue) — three shapes for one concept. Lab TAT compliance appears on both Executive and Laboratory from unrelated sources. The shared-dataset work should collapse these to one canonical series each, with secondary pages linking rather than re-deriving.

**6. Roughly a third of loaded fields are never encoded, and several targets are hard-coded in route files.** Fields fetched and then discarded or relegated to tooltips include `DiagnosisRow.caseRate`/`avgLos`/`trend` (on the chart), `DenialReason.valueAtRisk`, `LabTatCategory.median`, `CriticalResponseBar.sampleSize`, `AbnormalTestRow.totalResults`, `HandHygieneUnit.observations`, `SpecialtyAcceptance.avgResponseHours`, `ARPatientRow.lastBillingAction`, `SsiSurgeon.department`, `OrBlock.surgeon`, `LabWorkloadRow.ordersCompleted` and `FormularyRow.inNf`. Separately, thresholds that ought to be data are embedded in route code: `borStatus()`, `alosStatus()`, `daysInArStatus()`, `collectionStatus()`, `writeOffStatus()`, `denialRateStatus()`, `hacStatus(v, 4.1, 0.7)`, `tatStatus()` and `GENERIC_SUBSTITUTION_TARGET = 80`. The shared dataset should carry targets and benchmarks as fields so charts can render them as reference lines rather than as colour tones whose rules are invisible to the reader.

**7. D3 is genuinely warranted in exactly one place today.** Clinical's **Referral Flow** is a hand-rolled 2-column SVG whose node rectangles are a fixed 18px regardless of throughput and whose links are evenly distributed rather than volume-packed — `d3-sankey` would fix both, and the dependency is already installed and already used by chart 13 in `Top20NewCharts.tsx`. Four further cases are conditional rather than clear: D3 `treemap` + zoom for Clinical's Procedure treemap and Claims' Case Type treemap *if* true hierarchical drill-in becomes a requirement; `d3-force` beeswarm for Laboratory's Individual Notification Times *if* the grouped-by-department redesign is adopted; and matrix seriation for the Readmission Matrix *if* it grows well past 5×8. Everything else on the site — SPC control charts, funnel plots, waterfalls, box plots, bubble quadrants, stacked areas, heat grids — is either already well served by Recharts or already competently hand-rolled in SVG, and should stay that way.
